# Deviations from the decomp

The port is a hard fork of infernal-machine-decomp at upstream commit `319a6fc22c515900c8dd126632a3944507abc984`
(this repository's first commit). This file records every intentional change to the imported sources, grouped by kind,
so that upstream fixes can still be cherry-picked and so "port bug" and "behaviour change" stay distinguishable.
The plan these follow is `PORT-PLAN.md`.

Changed code is marked in the source with a `// Port:` comment where the reason is not obvious from the diff.

## Phase 0: bootstrap

### Build

- CMake replaces the decomp's ninja/python matching pipeline (`configure.py` is not used). Targets: `zlib`, `std`,
  `rdroid`, `sound`, `smush`, `sith`, `platform`, `jones3d`. Flags and rationale are in `CMakeLists.txt`.
- `Libs/j3dcore/j3d.h` is still generated from `j3d.h.in` by `configure_file`.
- `NDEBUG` is defined unless `J3D_DEBUG_ASSERTS=ON`, matching the decomp's release build.

### Headers

- `Libs/j3dcore/types.h`: the 1999 ABI integer typedefs (`int32_t`, `uintptr_t` as `unsigned int`, ...) are replaced
  by `<stdint.h>`/`<stddef.h>`. The count-fit (`CF_*`) macros are removed, and so is every `CF_*` block in the `.c`
  files (they were placeholder declarations that only padded VC5's symbol tables).
- `Libs/j3dcore/j3d.h.in`: the `_WIN32` branch is replaced. `J3DAPI` is empty, `J3DNORETURN` is `_Noreturn`,
  `strcmpi`/`strncmpi`/`wstrcmpi`/`wstrncmpi` map to the POSIX case-insensitive functions.
- `__inline` becomes `static inline` (`rdVector.h`, `stdMath.h`). `rdVector.c` keeps the external definitions.

### Win32 shim (debt)

`platform/apple/shim/` provides `Windows.h`, `ddraw.h`, `d3d.h`, `dinput.h`, `dsound.h` (gone since P4.11), `dplay.h`,
`commdlg.h`, `CommCtrl.h`, `io.h` and friends, which forward to `win32_shim.h`, `win32_shim_dx.h` and
`win32_shim_gui.h`. They hold only the types, constants and prototypes that otherwise-portable code names. The goal
(Phase 7) is to delete them.

### Excluded sources

Replaced by `platform/` (see `CMakeLists.txt` for the phase that brings each real backend):
`std/Win95/{std3D,stdDisplay,stdControl,stdComm,stdConsole,stdWin95,stdGuid}.c`, `sound/Driver.c`,
`smush/insane/{Timer/Timer,Sound/Dsnd,File/Stdfile,File/Stdio}.c`. Dropped entirely:
`rdroid/Primitives/rdModel3K.c` and `rdModel3K_cpu.c` (SSE "Katmai" path), `sith/World/sithWrite.c` (debug-only).

### Null platform

`platform/common/null/*_null.c` are generated by `tools/gen_null_platform.py` from the public headers of the replaced
modules: every function exists and returns zero/NULL unless the script gives it an override. `win32_null.c` and
`wkernel_null.c` are hand-written (message queue, quit handling). `platform/common/crt_posix.c` holds real POSIX
implementations of the MSVC CRT/kernel32 calls with an exact equivalent (`_findfirst`, time, sleep, directories).

### 64-bit fixes made to compile

Pointer-to-`int` casts are hard errors (`-Werror=pointer-to-int-cast`, `-Werror=int-to-pointer-cast`), so these were
fixed in Phase 0. They are layout-neutral for anything read from disk; the on-disk audit is Phase 1.

| Where | Change |
| --- | --- |
| `sound/Sound.c` | `Sound_LoadStatic`'s `uint32_t[2]` {marker, pointer} becomes `SoundStaticIdx` {marker, pointer}. |
| `sound/types.h` | `SoundDriverGetSoundBufferDataFunc` size out-param is `size_t*`, as its definition already was. |
| `std/General/stdMemory.c` | Allocation-header `id` stores the low 32 bits of the header address. |
| `std/General/stdFileUtil.c` | `_findfirst` handle compared as `intptr_t`. |
| `zlib/gzio.c` | The FILIO file handle in `gz_stream` is `intptr_t` (it holds a pointer). |
| `smush/insane/filio.h`, `Cdstream.h`, `Timer.h`, `animplay.h`, `LecShare.c` | File handles, stream `Advance`, timer and `Play` arguments widened to `intptr_t`. |
| `Jones3D/Display/jonesConfig.c` | Dialog init args and stored `WNDPROC`s widened to `intptr_t`/`LONG_PTR`. |
| `sith/*`, `rdroid/*`, `Jones3D/*` (various) | `NULL` assigned to integer handles becomes `0`; other pointer/int casts go through `intptr_t`. |

### Other

- `std/General/std.c`: the x87 control-word code is compiled out; `stdMath.h` uses its `NONMATCHING_MATH` C bodies.
- `sound/AudioLib.c`: the inline-asm sample loop has a C translation (verified in Phase 4).
- `Jones3D/Display/jonesConfig.c`: one function with a bare `return;` in a non-void function (a retail bug) returns 0.

## Phase 1: headless boot

### Settings and data root

- `platform/common/wuRegistry_file.c` replaces the registry (and the Phase 0 in-memory store). Same value names, stored
  in `~/Library/Application Support/J3DPort/settings.ini` (`J3D_SETTINGS` overrides the path). Format and lookup order
  are documented at the top of the file. `J3D_REG_<name>` environment variables override any value.
- `Data Root` (from `--data <dir>`, `J3D_DATA`, or the file) is the folder that holds `RESOURCE/`. It is the default for
  `Source Dir`, `User Path` and `Install Path`, so JonesFile's install and CD roots both resolve to the player's data.
- `Start Mode`, `Debug Mode` and `Verbosity` default to 0, 1 and 2 (start game, console log, verbose) until the GUI
  exists. They are defaults, not stored values.

### Paths

- `stdFnames` accepts `\` and `/` as separators and builds paths with `/`.
- `stdGob_FileOpen` folds `/` to `\` before its directory lookup; names inside GOBs are unchanged.
- `platform/common/host_path.h`: `J3DHost_ToPosixPath` is the single engine-to-host path conversion, used by
  `stdFileOpen` and every CRT/kernel32 path call in `crt_posix.c`. It translates `\` and resolves each component
  case-insensitively when the path does not exist as spelled.
- Parsers that looked only for `\` also accept `/`: `stdFileFromPath` (object names of cogs, models, particles),
  the `__FILE__` stripping in `stdPrintf`, `stdPlatform_Assert` and `JonesMain`'s assert handler, the NDS file name in
  `JonesMain`, and the install-path prefixing in `sithMain`. The `jonesConfig.c` path code is left for Phase 6.
- The three engine sites that call `fopen` directly on a built path (the quick-save probe and `JonesError.txt` in
  `JonesMain`, the keyset writer in `jonesConfig`) use `J3DHost_fopen`. Before, `JonesError.txt` was created with the
  literal name `.\\JonesError.txt`.
- `stdFnames_Concat` checks for an empty `path1` before reading `path1[len - 1]` (retail read one byte before the buffer).

### 64-bit audit: on-disk layouts

`tools/layout_audit.py` compiles every translation unit that reads or writes raw structs twice, for arm64 and for i386
with MSVC's double alignment, and diffs clang's record layouts for the audited on-disk types. It must report
`0 retail on-disk type(s) differ`. Each fixed record also carries a `_Static_assert` on its retail size.

| Where | Problem on arm64 | Change |
| --- | --- | --- |
| `sithWorld.c` `CndWorld` | `size_t` AI-class and sprite counts; the loader read the header straight into `SithWorld`, whose pointers are 8 bytes, so every count after the first pointer landed in the wrong field | All fields fixed-width (0x61C bytes). The header is read into a local and `sithWorld_CopyCndHeader` copies the scalar fields; pointer fields stay NULL. |
| `sithThing.c` `SithThingBinaryHeader`, `SithAIBinaryRecord`, `SithParticleBinaryRecord` | `size_t` counts (header 44 vs 88 bytes) | `uint32_t`. |
| `sithThing.c` path frame counts | array of `size_t`, sized `numPathThings * sizeof(size_t)` | `uint32_t`. |
| `sithSurface.c` `totalVerts`, `sithMaterial.c` `sizePixelBuffers` | `size_t` read and written with `sizeof(var)`, 8 bytes against a 4-byte field: misaligns the rest of the section | `uint32_t`. |
| `sithPVS.c` PVS size | 4-byte read into a `size_t` field | Read into a `uint32_t`, then assigned. |
| `Sound.c` `SoundInfo` in .cnd sound banks | in-memory record (pointer `pLipSyncData`) written and read raw | `SoundInfoFile` is the 48-byte on-disk record; export/import convert. Import clears `pLipSyncData` (the stored value is a pointer from the writing process; lip-sync data is regenerated on demand). The used-cache size is read through a `uint32_t`. |

Not affected: `SithCogValue` (cog symbol values are stored as strings in .cnd files; the union only reaches disk in
savegames), all `.mat`, GOB, BMP and font records, and the string tables (narrow text, widened in memory).
Savegames (`NdsHeader`) differ but are only read back by the port; the round-trip test covers them.

### 64-bit audit: text parsing and memory safety

- 24 `sscanf` conversions wrote `%d` (4 bytes) into `size_t` counts in the 3DO model, keyframe, particle and level
  text parsers and the `-level` command-line number, leaving the upper half uninitialised. They use `%zd`
  (clang's fix-it; same signed parse, size_t width). Every `sscanf` in the tree has a literal format, so `-Wformat`
  checks all of them.
- `JonesHud.c`: two 16-byte `memset`s from `&jonesCog_bShowHealthHUD` relied on VC5 laying out four globals adjacently;
  the four flags are cleared individually.
- `jonesConfig.c` `EditControlScheme_DeleteAssignment`: the index locals are `size_t`, as the callee writes.
- `JonesFile.c`: the file-name terminator is written to the last byte of `aName`, not one past it.

### 64-bit audit: index arrays

Found by the level-load test, not by the layout audit: these are in-memory arrays of `size_t` whose allocation or
copy still assumed 4-byte elements.

| Where | Problem on arm64 | Change |
| --- | --- | --- |
| `sithSector.c` `aVertIdxs` (text and binary readers) | allocated with `sizeof(int)` / `sizeof(int32_t)` per element: half the size of the `size_t` array, so the loader wrote past the allocation | `sizeof(size_t)`. |
| `sithSector.c` binary reader and writer | `memcpy` between the file's `int32_t` indices and the `size_t` array packed two indices into each element | Converted element by element. |
| `sithSurface.c` `face.aVertices`, `face.aTexVertices` (text and binary readers) | allocated with `sizeof(int)` per element | `sizeof(size_t)`. |
| `rdModel3.c` `rdModel3_LoadEntry` face `aVertices`, `aTexVertices` | allocated with `sizeof(int*)`, which is the right size on arm64 only by coincidence | `sizeof(size_t)`, the element type. |

### Loading without a display

Materials and fonts are converted to the renderer's texture format while a level loads, so the loaders need working
VBuffers and a texture format even when nothing is drawn.

- `platform/common/stdDisplay_vbuffer.c` implements `stdDisplay_VBufferNew`, `VBufferFree`, `VBufferLock`,
  `VBufferUnlock`, `VBufferSetColorKey` and `VBufferConvertColorFormat`. They are the system-memory branches of the
  retail `stdDisplay.c` functions; the DirectDraw-surface branches do not exist in the port. One change:
  `VBufferNew` frees the header when the pixel allocation fails (retail leaked it). The display backend of Phase 2
  keeps this file.
- `tools/gen_null_platform.py` has an `IMPLEMENTED_ELSEWHERE` set. Functions named there are left out of the generated
  null file; this is how a real implementation replaces part of a null backend (PORT-PLAN.md decision 13).
- The null `std3D_GetTextureFormat` reports 32 bpp BGRA (alpha in the top byte for the two alpha formats, none for
  RGB) with no colour key, which is the layout the Metal backend will upload. `std3D_GetColorFormat` is the retail
  body: it is a pure function of the colour info.
- `sithMaterial_ReadMaterialsListBinary`: retail allocated one VBuffer per mip level and reused it for every cel.
  That only works while the texture format has the source's bit depth (16 on the cards of 1999), because
  `VBufferConvertColorFormat` replaces a buffer whose depth differs, after which the copy and the advance through the
  source pixels used the converted size. The port allocates a buffer in the source format for every cel and mip,
  advances by the source size, and frees the converted buffers after upload. The retail body is kept under `#else`.

### Loose-file overrides

- `JonesFile_Open`: retail's `Indy3D.exe` ran from `<install>\Resource`, so its "current directory" search root was the
  resource folder, and that is how the loose files there (the 1.2 update's patched cogs in `Resource\Cog`) overrode GOB
  contents. The port runs from anywhere, so when a CD path is set that root is the CD resource folder instead (the data
  root's `RESOURCE/`), searched for loose files only (its GOBs are already open as the CD resource). Without a CD path the retail behaviour
  is unchanged.

### Diagnostics added

- `stdFileOpen`: `J3D_TRACE_FILES=1` prints every host file that opens successfully to stderr, which shows which loose
  files are overriding GOB contents.
- `sithWorld_LoadEntryBinary` reports a short header read, a copyright-block mismatch, and the name and file offset of
  the section that failed. Retail reported only "Parse problem" for the whole file.

### Build and tests

- The game shell (`Jones3D/*.c`) is the static library `jones3d_game`; `jones3d` is `platform/apple/main.c` linked to
  it. The tests link the same library without the entry point.
- `tests/harness.c` starts the engine in `JonesMain_Startup`'s order without display, input, sound output or dialogs,
  keeps the player's settings file out of it (`J3D_SETTINGS` defaults to `/dev/null`), and installs assert and crash
  handlers that print a backtrace.
- `tests/levelload.c` loads the static world and all 17 levels and prints each level's section counts.
  `tests/cogcheck.c` compiles every `.cog` in the three GOBs through the engine's lookup, so a loose override is the
  file compiled. `tests/saveload.c` is the savegame round trip ("Savegame round trip"). All three, and `boot` (see
  "Headless run"), are registered with `ctest` when the tree is configured with `-DJ3D_TEST_DATA=<data root>`.
  A new test is a file in `tests/` and its name in `J3D_TESTS` (`CMakeLists.txt`).
- `tools/gobtool.py` lists and extracts GOB contents. Nothing in the build depends on it.
- `docs/BUILDING.md` is the port's build guide. The decomp's file of that name is now `docs/DECOMP-BUILDING.md`, and
  the links to it in `DECOMP-README.md`, `BUILD-PIPELINE.md` and `REPRODUCIBILITY.md` were repointed. Its text is
  unchanged.

### Headless run

`jones3d --headless --frames <n>` runs the real game loop with no window, renderer, input or sound, for tests
(PORT-PLAN.md P1.17, P1.18). `ctest` runs it for 600 frames as the `boot` test.

- `platform/common/null/stdDisplay_headless.c` (moved from `platform/common/` in P2.3, see "Display device and
  modes") is the null build's display device, in memory: one device and one 640×480 32 bpp mode. The queries, the
  system-memory back buffer, fill, lock and `SaveScreen` are in `platform/common/stdDisplay_common.c`. These functions
  are named in the generator's `IMPLEMENTED_ELSEWHERE`. `stdDisplay_Open` still fails, as in Phase 0, unless
  `J3D_HEADLESS` is set (`--headless`). `stdDisplay_VBufferCopy` and the GDI device-context functions remain null.
- The null `std3D` starts and opens and reports one device; `std3D_GetValidDimensions` returns the size asked for.
- `platform/common/host_clock.h`, in `crt_posix.c`: `timeGetTime`, `GetTickCount` and `Sleep` run on a virtual clock
  once the headless display opens, starting at a fixed 10,000,000 ms (see "Savegame round trip"). It advances 33 ms
  for every `stdDisplay_Update` and by the requested time for every
  `Sleep`, and never by itself. A headless run is therefore not tied to real time (600 frames take about 0.3 s) and
  its log is identical from run to run.
- `wkernel_null.c`: `J3D_FRAMES=<n>` (`--frames <n>`) ends `wkernel_Run`'s loop after n passes through
  `JonesMain_Shutdown`, the path a closed window takes.
- The null Win32 has memory DCs and DIB sections (`CreateCompatibleDC`, `CreateDIBSection`, `GetObject`, `DeleteObject`,
  `DeleteDC`): `jonesConfig_Startup` loads the dialog icons through `stdBmp_Load` and the HUD will not open without
  them, and `sithGamesave` writes the savegame thumbnail from one. `StretchBlt` is still a no-op, so the thumbnail
  in a save is black until Phase 6.

### Where the port writes

PORT-PLAN.md P1.19. Retail wrote under its install folder; the port never writes to the player's game data
(`platform/common/host_dirs.h`).

- `Install Path` is the setting the engine writes under: `SaveGames/` and `ScreenShots/` (`sithGetPath`) and
  `KeySets/` (`jonesConfig_InitKeySetsPath`). Its default is now `~/Library/Application Support/J3DPort/`, the folder
  of `settings.ini`, instead of the data root. `Source Dir` and `User Path`, which the engine reads game files from,
  still default to the data root.
- `J3DHost_PrepareUserDirs`, called by `platform/apple/main.c` before `WinMain`, creates the effective `Install Path`
  and, when its `KeySets/` does not exist yet, copies the retail `*.kfg` files from the data root's `KEYSETS/` into
  it. An existing `KeySets/` is never refilled, so deleted keysets stay deleted. The test programs do not call it, so
  they write nothing under the user's Library.
- `JonesMain_LogErrorToFile` writes `JonesError.txt` to `~/Library/Logs/J3DPort/` (or `J3D_LOGS`) instead of under
  `Install Path`, and its path buffer is 1024 bytes instead of 128. `JonesLog.txt` (log-file output mode) goes to the
  same folder instead of the current directory. The folder is created when the first log is written.

### Compiler warnings (P1.23, P1.24, P1.28)

Every warning class except narrowing is now closed and the build uses `-Werror` (`CMakeLists.txt`). The exceptions
are listed in "Known open items".

- **`rand` (P1.24).** `j3d.h` maps `rand()` and `srand()` to `J3DHost_rand` and `J3DHost_srand` in `crt_posix.c`, the
  Visual C++ generator (`seed = seed * 214013 + 2531011`, 15-bit result, seed 1), and sets `RAND_MAX` to `0x7FFF`.
  The engine never seeds it, so it draws retail's sequence. macOS `rand()` returned 31 bits, which changed every
  `rand() % n` and made `SITH_RAND`'s `1.0f / RAND_MAX` inexact (the 144 constant-conversion warnings). The macros are
  function-like, so struct members named `rand` are untouched.
- **Formats (P1.23).** `size_t` values printed with `%d` now use `%zu`/`%zd`; the output is unchanged for values that
  fit in 32 bits. INSANE's debug allocator printed `int`s with `%ld` and pointers with `%08lx` (`%d`, `%p` now).
  `sithCog_SendMessageEx`'s debug trace printed its `int` params with `%g` (retail printed garbage; `%d` now). The
  horizon and ceiling sky offsets were scanned with `%f` into the `rdVector2` itself (now `.x`; same address).
- **Messages used as format strings (P1.28).** `JonesMain_LogErrorToFile`, the log-file writer, `std.c`'s file-name
  prefix, the keyset writer in `jonesConfig.c` and the colour-depth strings of the display dialog passed text as the
  format string. They now use `"%s"`. No string in `jonesstrings.uni` contains `%%`, so the output is the same.
- **The rest of P1.28.** Include spellings now match the files on disk (11). The static resource indices passed to
  `sithModel_GetModelByIndex` are cast to `int16_t` explicitly (the value retail passed). `rdSprite.c` tested
  `fabs(lvec.z >= 0.9999f) != 0.0`, which is `lvec.z >= 0.9999f`, now written so. Two tests of an array's address,
  which is never null, are now unconditional (`sithThing.c` explosion sprite name, `jonesConfig.c` keyset folder).
  `sithCollision.c` had `p = p = next`. The rest are casts that state what retail did (`const` discarded, enum
  pointers, `abs` of a `UINT`, the `WS_POPUP` style bits, a `tFileHandle` compared with `NULL`).

### Sanitizer findings (P1.21)

`-DJ3D_SANITIZE=ON` builds with ASan and UBSan (docs/BUILDING.md). All four tests pass under it, as does a 3,000 +
3,000 frame `saveload` run. What it found:

| Where | Problem | Change |
| --- | --- | --- |
| `std/General/stdMemory.c` zone allocator | Blocks rounded to 4 bytes: the 16-byte zone headers and the blocks after them were only 4-byte aligned on 64-bit | Blocks round to the pointer size; the zone size is a multiple of it. |
| `std/General/stdMemory.c` debug allocator | The guard word after each block was stored and checked through a `DWORD*` at an arbitrary offset | `memcpy`. |
| `sith/Gameplay/sithEvent.c` `sithEvent_ResetFreeBufferTable` | The loop ran to `i = 0` and wrote `-1` one element past the free-index table, into the next global | Stops at 1; the 256 entries are the same. |
| `std/General/stdConffile.c` `stdConffile_ReadLine` | A one-character line (the last line of a file with no newline) read `stdConffile_aLine[-1]` | Length guard. |
| `smush/insane/Lec/LecShare.c` | The backward registry walks formed `&entries[n - 1]` with `n = 0` | `entries + n - 1`; it was never dereferenced. |

### Savegame round trip (P1.20)

`tests/saveload.c` runs the game headless (as `jones3d --headless` does, through `JonesMain_Startup` and the game
loop), saves with `sithGamesave_SaveFile`, records the world, restores with `sithGamesave_RestoreFile`, records it
again and compares: thing count and, per thing, index, type, guid, signature, flags, position (bit for bit), sector
and health; the 16 COG globals; game time; the player thing. It then saves the restored game and compares the two
files message by message, and plays 300 more frames.

Two headless runs used to write autosaves that differed in 74 bytes although their logs matched. The causes, all
fixed:

- **COG globals in the header.** `sithGamesave_SaveFile` copied each global symbol's whole value. On 64-bit the value
  union is 16 bytes, and an `int` or `float` symbol keeps stale pointer bits above its 4 bytes. Only the member the
  type names is copied now; pointer, symbol-id and string values are still reset, as retail did.
- **Sprite things.** `sithDSSThing_FullDescription` writes a model index and the model's `insertOffset` for any thing
  whose `renderData.data` (a union) is set. For a sprite that pointer is an `rdSprite3`, its model index is -1, and the
  12 bytes written came from the sprite (on 64-bit, a heap pointer). `sithDSSThing_ProcessFullDescription` reads no
  vector after a -1, so it took those bytes as the thing's alpha and the rest of the record: a restored sprite got a
  garbage alpha. The writer now writes the vector only with a real model index. This is a retail bug fix, but retail's
  behaviour (bytes from the sprite at a 32-bit `rdModel3` offset) cannot be reproduced on 64-bit anyway.
- **Absolute times.** The sound section stores times taken from `timeGetTime`. The headless virtual clock started at
  the real uptime, so they changed from run to run. The host clock now counts from process start (plus 1000 ms), and
  the virtual clock starts at a fixed 10,000,000 ms.

A save of the restored game is not byte-identical to the original save, in three ways that are retail behaviour and
are left for the OpenJones3D fix series in Phase 8 (decision 11). The test allows exactly these:

- AI status messages come out in a different order: AI control blocks are reallocated on restore.
- An animation's ID is `(player + 1) << 16 | slot`, and restore reallocates slots from 0 with no holes, so IDs change.
  A COG that kept an animation ID across a save would lose it. (`sithDSS_ProcessAnimStatus`, `sithAnimate_NewAnim`.)
- `Sound_Save` writes `now - pauseStart`; `Sound_Restore` sets `pauseStart = saved + now`. Only the sound section's
  fifth word differs. To be looked at with the rest of the sound restore in Phase 4.

### Path length (P1.30)

The engine kept file paths in 128-byte buffers (`SITH_PATHSIZE`, `STDCONFFILE_FILENAMESIZE`,
`JONESCONFIG_GAMESAVE_FILEPATHSIZE` and many `char[128]` locals). With a long `Install Path` the autosave name was cut
to `st`, the save was then not recognised as an autosave and the level played differently; with a long data root the
GOBs were not found. `j3d.h` defines `J3D_PATHSIZE` (1024), and every buffer that holds a host path now uses it: the
three constants above; the save, screenshot, keyset, log and resource paths in `sithMain.c`, `sithGamesave.c`,
`sithRender.c`, `sithCogFunction.c`, `JonesMain.c`, `JonesFile.c`, `JonesHud.c` and `jonesConfig.c`'s keyset code; the
resource and GOB path fields (`JonesResource.aPath`, `sGob.aFilePath`, `FindFileData.aSearchFilter`,
`JonesState.aInstallPath`, `aCDPath`). `stdConffile_PushStack` asserted `< 128`. `JonesMain`'s error messages that
include a path use `snprintf` into a wider buffer. None of these is an on-disk record (`layout_audit.py` still reports
0). `boot`, `saveload`, `levelload` and `cogcheck` pass with a 257-character `Install Path` and a 229-character data
root. The file dialogs in `jonesConfig.c` still use 128-byte buffers; Phase 6 replaces them (P6.17, P6.24).

### 64-bit audit: narrowing conversions (P1.25 to P1.29)

All 510 `-Wshorten-64-to-32` warnings outside `jonesConfig.c` were triaged, and `J3D_WERROR_SHORTEN` is now on by
default. Each was classified by what the converted value can be:

- **Bounded values** (about 440): counts and indices of engine arrays, string lengths, pointer differences within one
  array, `ftell` of a game file, `lrintf` results, `time_t` file times (fit until 2106), Win32 message results. Retail
  computed them in 32 bits, so an explicit cast is exactly retail's value. Each is written `(T)expr` and marked
  `// Port: narrowing cast`. They were inserted with clang's own source ranges, so the cast covers exactly the
  converted expression.
- **Values that were wrong on 64-bit**, fixed by type instead:
  - INSANE's `FilioHandle` (a host `FILE*`) was kept in `int` variables in `Cdstream.c` (`Stream.hFile` and two
    locals) and `Zfilio.c`: the handle was truncated. Movies would have crashed on their first read in Phase 5.
  - `D_bloc16.c` stored the distances from the current Blocky16 frame to the two previous ones, three separate
    allocations, in `int`. They are `ptrdiff_t` now, as are `dbloc16_Codec2`'s parameters (P5.7 translates it).
  - `rdCache_ProcFaceCompare` returned `pMat2 - pMat1`. Static-world and level materials are separate allocations, so
    the difference can exceed 32 bits and flip sign, which breaks the face sort. It returns the sign of the comparison.
  - The HUD's millisecond timers (`JonesHud_msecTime` and four more, and the update's `curTime`) were `size_t`. They
    are `uint32_t`, retail's `DWORD`, so their arithmetic wraps at 2^32 like `timeGetTime`.
  - `SITHDSS_ENDOUT` computes the message length from a pointer difference within the message buffer; the cast is in
    the macro.
- `jonesConfig.c`'s 58 are Win32 dialog message plumbing (`WPARAM`, `LRESULT`, list-view item data) that Phase 6
  rewrites (P6.24). That one file is compiled with `-Wno-error=shorten-64-to-32`.

Behaviour is unchanged: the `boot` log is identical before and after, and the four tests pass.

## Phase 2: display and renderer

### Build (P2.1)

- `J3D_PLATFORM` (`apple`, the default, or `null`) selects the backends of the `jones3d` binary. `apple` enables the
  `OBJC` language, requires the SDL3 CMake package (3.2 or later) and links SDL3, Cocoa, Metal and QuartzCore.
  `null` builds without either, as phases 0 and 1 did.
- The single `platform` library is split in three: `platform_core` (`platform/common/*.c`, shared), `platform_null`
  (the generated null backends) and, in an apple build, `platform_apple` (`platform/apple/*.c` and `*.m` except
  `main.c`, plus the null files no Apple backend replaces yet, listed in `J3D_APPLE_REPLACES_NULL`). `jones3d_game` no
  longer links a platform: each executable links `jones3d_game` and one platform library (`j3d_executable` in
  `CMakeLists.txt`).
- The test programs always link `platform_null`. An apple build also produces `jones3d-null`, `main.c` with the null
  backends, and the `boot` test runs that, so the headless tests never depend on SDL or Metal.
- Objective-C is compiled with ARC and the same warning set as C. Objective-C files sit behind C headers
  (`platform/apple/host_apple.h`), so no engine file includes an Objective-C header.
- `platform/apple/host_apple.m`: `J3DApple_LogHostInfo`, called by `main.c` in the apple build only, prints the macOS
  version, the default Metal device and the SDL3 version before the engine starts.
- Homebrew's SDL3 is built for the host's macOS version, so linking `jones3d` against it prints one linker warning (one per program that links SDL3: since P2.10 also the `present` and `render` tests)
  (`building for macOS-13.0, but linking with dylib ... built for newer version`). It goes away when SDL3 is shipped
  inside the bundle, built for the deployment target (PORT-PLAN.md P8.3). Until then the binary runs only on macOS
  versions as new as the build machine's SDL3.

### Window and event loop (P2.2)

- `platform/apple/wkernel_sdl.c` replaces `wkernel_null.c` in the apple build. It keeps retail `wkernel.c`'s shape:
  `wkernel_Run` creates the window, runs `JonesMain_Process` until it returns 1 or -1, and a private
  `wkernel_MainWndProc` handles `WM_CLOSE` (shut the game down, destroy the window) and `WM_DESTROY` (post the quit)
  before handing every other message to the procedure the game installed. The window's `HWND` is its `SDL_Window*`.
- SDL events are translated into the Win32 messages the two game window procedures handle; the table is at the top of
  the file. Keys carry `VK_` codes (letters by the layout's symbol, everything else by position) and the repeat,
  extended and transition bits; the scancode field of `lParam` stays 0 until Phase 3's DIK table. `WM_CHAR` comes from
  SDL text input converted to Windows-1252, plus Backspace, Tab, Return and Escape, which `TranslateMessage` produced
  from the keys. Mouse messages carry back-buffer coordinates since P2.15 (window coordinates before).
- Activation messages are sent on a change of focus only. The window counts as active from the start, because the
  retail game installed its window procedure after the window's first activation and never saw it
  (`JonesMain_bAppActivated` starts at 0).
- `PostMessage`, `PostQuitMessage`, `SetTimer` and `KillTimer` for the game window are real (the quicksave text uses a
  timer). Timers run on the engine clock (`GetTickCount`), so the virtual clock of a headless run drives them too.
  Messages and timers for other windows are refused or dropped until the dialog system (Phase 6). To make this
  possible the generator writes those four functions and the null queue state to their own file,
  `win32_msg_null.c`, which the apple build leaves out with `wkernel_null.c` (`J3D_APPLE_REPLACES_NULL`).
- `--headless` selects SDL's `dummy` video driver unless `SDL_VIDEO_DRIVER` is set, so the apple binary runs headless
  through the same event loop. `boot-sdl` (`ctest`, apple builds) is `boot` run that way; its log matches the null
  run's line for line (apart from the `Host:` line, and since P2.3 the display lines) and its autosave is
  byte-identical.
- `wkernel_SetWindowStyle` makes the window bordered for a style with `WS_CAPTION` (windowed mode) and borderless
  otherwise; `wkernel_SetWindowSize` sets the client size (since P2.3 not while the window is fullscreen, see "Display
  device and modes"). Resizing, the fullscreen toggle and minimizing came with P2.19 ("Window behaviour").
- `platform/apple/main.c`: retail returned 1 from `WinMain` for every normal quit (`WM_QUIT`). The process now exits 0
  for 0 and 1 and fails for -1 (startup failed). A `--frames` run must return 0 (its frame count reached); one that
  ends earlier, for example because a level failed to load and the game closed itself, still fails.
- The shim gained the `VK_OEM_*` punctuation key codes.
- Checked by hand: with `SDL_VIDEO_DRIVER=cocoa jones3d --headless` a 640x480 window opens, the game runs, and SIGTERM
  (SDL's quit event, the same path as Cmd-Q and the close button) shuts it down cleanly with exit 0, also under the
  sanitizers. Not checked by script, because macOS does not let a background process take focus: the pause on focus
  loss and the key messages. Phase 3 brings scripted input.

### Display device and modes (P2.3)

- `stdDisplay` is split by what changes between backends. `platform/common/stdDisplay_common.c` (every build) has the
  queries (`GetNumDevices`, `GetDevice`, `GetCurrentDevice`, `GetNumVideoModes`, `GetVideoMode`,
  `GetCurrentVideoMode`, `IsFullscreen`, `CanRenderWindowed`), `FindClosestMode` (the retail body, unchanged),
  `SetDefaultResolution`, `ClearMode` and the 32 bpp system-memory back buffer with its fill, lock and `SaveScreen`.
  A backend supplies the device and mode list and the window side: `Startup`, `Shutdown`, `Open`, `Close`, `SetMode`
  and `Update`. The null build's backend is `platform/common/null/stdDisplay_headless.c` (unchanged in behaviour); the
  apple build's is `platform/apple/stdDisplay_sdl.c`, which leaves the headless file out
  (`J3D_APPLE_REPLACES_NULL`). The retail statics they share (`stdDisplay_aVideoModes`, `stdDisplay_numDevices`,
  `stdDisplay_primaryVideoMode`, `stdDisplay_bFullscreen`) are declared in `platform/common/stdDisplay_common.h`.
- `stdDisplay_sdl.c` reports one display device: the display the game window is on, named after it, with the driver
  name `SDL <video driver>` (stored as the `Display` setting), 3D capable and able to render in a window.
- The mode list is all 32 bpp (BGRA, the back buffer's format). It holds, in pixels: the desktop's size; the 4:3
  sizes 640×480, 800×600, 1024×768, 1152×864, 1280×960 and 1600×1200 that fit the desktop; and the display's own
  fullscreen modes no larger than the desktop, without duplicates, at most 64 (the retail array), sorted as retail
  sorted them (bpp, width, height). The desktop size and 640×480 are always present. A mode's pixel size is SDL's
  point size times its pixel density, so a Retina display's native size is listed. On the development machine
  (2560×1440 display) that is 14 modes; SDL's `dummy` driver (headless) gives 3, from its 1024×768 desktop.
- Fullscreen does not change the display mode, which retail's DirectDraw exclusive mode did. A fullscreen mode makes
  the window cover the display at the desktop's own mode, and the back buffer has the mode's size; the present path
  scales it to the screen (P2.6). `stdDisplay_Close` takes the window out of fullscreen, as releasing DirectDraw gave
  the desktop its mode back. `wkernel_sdl.c` turns off SDL's macOS Spaces fullscreen
  (`SDL_HINT_VIDEO_MAC_FULLSCREEN_SPACES`): it is animated, and macOS ignores it for an app that is not frontmost
  (found when testing from a script: the window stayed 640×480). `wkernel_SetWindowSize` leaves a fullscreen window
  alone: retail's window already matched the screen in a fullscreen mode, and SDL would shrink it to the size given.
- `stdDisplay_Update` presents through Metal since P2.6 ("Present path"). Headless, it moves the virtual clock by 33 ms
  as before.
- `stdDisplay_Open` with a device number equal to the device count fails; retail tested `>` and would open one past
  the end of the device array.
- `stdDisplay_GetCurrentDevice` reports the open device and fails when none is open; retail copied device
  `stdDisplay_curDevice` whenever any device existed. `stdDisplay_SetDefaultResolution` rebuilds the whole windowed
  mode, so its row size and byte size follow the new size (retail stored only the width and height).
- The null `std3D_BuildDisplayEnvironment` (generator override) now enumerates as retail `std3D.c` did: every
  `stdDisplay` device, opened and closed in turn, with its mode list, and the one null 3D device on each 3D-capable
  display. Before, it returned a fixed environment with one 640×480 mode, so the game never saw the SDL mode list and
  the `Width` and `Height` settings had no effect. As in retail, a device that cannot be opened fails the call; in a
  null build without `--headless` the game now stops there (the display error), a little earlier than before. The
  headless display now opens during this enumeration, so the virtual clock starts there instead of at
  `JonesDisplay_Startup`.
- `Jones3D/Main/JonesDevDialog.c`, `JonesDevDialog_FindClosestVideoMode`: retail looked only at 16 bpp modes (taking
  the one matching the `Width` and `Height` settings, otherwise the last 16 bpp mode). The port's modes are all 32 bpp,
  so it looks at those. Without the change no mode matched and the game always took mode 0. The display settings
  dialog's colour-depth handling is P6.16.
- Checked: `boot`, `boot-sdl` and the other tests pass in the apple, null and sanitizer trees; `boot-sdl` and `boot`
  still write byte-identical autosaves. With the Cocoa driver, `InWindow=1` and `Width`/`Height` 800×600 give an
  800×600 client area; the default settings (fullscreen, 640×480) cover the 2560×1440 display and leave fullscreen on
  exit, exit status 0.

### Back buffer (P2.4)

- The back buffer is a 32 bpp BGRX system-memory VBuffer in the mode's size (`J3DDisplay_CreateBackBuffer`), made by
  `SetMode` in both backends. `LockBackBuffer` hands out its pixels and pitch, `UnlockBackBuffer` does nothing (the
  pixels never move), `BackBufferFill`, `ClearRect` and `VBufferFill` fill it whole or by rectangle, and
  `GetBackBufferSize` reports it. All of it is in `stdDisplay_common.c`, shared with the headless display that
  introduced it in P1.17.
- Return values as retail: `stdDisplay_VBufferFill` returns 1 once it has filled (both retail branches did),
  `stdDisplay_BackBufferFill` returns 0 on success (retail returned `ColorFillSurface`'s 0), which
  `JonesDisplay_Startup` relies on, and 1 with no mode set. The headless display of P1.17 returned `VBufferFill`'s
  result from `BackBufferFill` and had `VBufferFill` return 0; no caller reads `VBufferFill`'s result.

### Blits (P2.5)

- `stdDisplay_VBufferCopy` is retail's `BlitSysToSys` (the system-memory pair of its four blit paths; every port
  VBuffer is in system memory) for 8, 16, 24 and 32 bpp, with the colour key for 8, 16 and 32 bpp as retail.
- Retail clipped against the destination only, in unsigned arithmetic, so a rectangle starting left of or above the
  destination with `x + width` still negative passed its "entirely outside" test and was read and written out of
  bounds; the source rectangle was not clipped at all. The port clips in signed arithmetic against both buffers. Every
  copy that retail performed in bounds is performed identically. Nothing in the game calls `VBufferCopy` today.
- `stdDisplay_EncodeFromRGB565` is the retail body (it builds the intro movie's colour table, Phase 5).
- Found, for Phase 5: the intro movie picks its blitter by comparing the mode's `ColorInfo` with fixed formats whose
  alpha fields are set (`alphaBPP` 8, shift 24). The port's mode reports no alpha, as retail's DirectDraw enumeration
  did, so no format matches and the intro is skipped. Phase 5 decides which side changes.

### Present path (P2.6)

- `platform/apple/display_metal.m` (C interface `display_metal.h`) presents the back buffer. `stdDisplay_SetMode`
  attaches it to the game window (a `CAMetalLayer` from `SDL_Metal_CreateView`; the window is created with
  `SDL_WINDOW_METAL` unless the video driver is SDL's dummy one) and `stdDisplay_Close` detaches it. Each
  `stdDisplay_Update` (retail's flip) uploads the back buffer into a texture, one of a ring of three so the CPU never
  writes one the GPU is reading, and draws it over the whole drawable with bilinear filtering: a 640×480 mode on a
  fullscreen 2560×1440 window is scaled to the screen (keeping its shape since P2.20). The drawable is the window's
  size in pixels.
- Presents wait for the display's refresh (`displaySyncEnabled`), which now paces a windowed run; the 60 Hz hold of
  P2.3 remains only for a window whose presenter failed to open. The game therefore runs at the display's refresh
  rate (60 or 120 Hz), faster than the 1999 hardware did; whether any game logic depends on frame length is for the
  visual pass (P2.22) and phase 7.
- A headless run with `SDL_VIDEO_DRIVER=cocoa` presents without waiting for the refresh, so the virtual clock still
  sets its pace; under the dummy driver nothing is presented.
- The shaders are compiled from source when the presenter opens. The fourth byte of a back-buffer pixel is ignored
  (X8R8G8B8); the drawable is opaque.
- Planned check not reachable in phase 2A: the plan's check for P2.6 was "the level-load progress screen is visible",
  but that screen is drawn through `std3D` (`rdWallpaper`), as is everything else the game draws apart from the intro
  movie (Phase 5). It becomes visible with the Metal renderer (P2.9 to P2.12). P2.6 is checked by the `present` test
  instead: a pattern drawn into the back buffer through `stdDisplay` is presented in a real window, read back from
  the drawable (`J3DMetal_ArmCapture`) and compared, at the back buffer's size and scaled to twice it. The test fails
  for a flipped image or a wrong clip in a blit (both tried).
- `stdDisplay_GetTextureMemory` and `stdDisplay_GetTotalMemory` (P2.8) report the Metal device's recommended working
  set as the total and what is not yet allocated from it as free (retail asked DirectDraw for video memory); the
  display device carries the same figures. The headless display reports a nominal 256 MB for both.

### Screenshots (P2.7)

- `stdDisplay_SaveScreen` writes the back buffer as a 24-bit BMP through `stdBmp_WriteVBuffer`, as retail.
- `Libs/std/General/stdBmp.c`, `stdBmp_WriteVBuffer`: retail computed the header's image size from the source depth
  (32 bpp, a third larger than the 24-bit rows it wrote) and wrote rows without the 4-byte padding BMP requires, so the
  file only read back right when 3 × width was a multiple of 4. The port pads the rows and sizes the header from them
  (`#ifdef J3D_PORT`, retail kept beside it).
- `jones3d --screenshot-at <n>[,<n>...]` (`J3D_SCREENSHOT_AT`) writes the back buffer after those passes of the game
  loop, to `--screenshot-file <path>` (`J3D_SCREENSHOT_FILE`; `{frame}` becomes the frame number; default
  `jones3d-{frame}.bmp` in the current directory), and reports each file on stdout

### Renderer skeleton (P2.9)

- The apple build replaces `std3D_null.c` with `platform/apple/std3D_metal.c` (the engine-facing `std3D`, in C) and
  `platform/apple/render_metal.m` (the GPU side, behind the C header `render_metal.h`). The split keeps the Win32
  shim's `BOOL` and Objective-C's apart and the Metal calls in Objective-C files only (strategy decision 5).
- `platform/apple/display_metal.m` became the shared Metal context (`display_metal_internal.h`, Objective-C only): one
  device and one command queue for the process, so all GPU work runs in commit order, and `J3DMetal_Commit`, which
  remembers the last command buffer so `J3DMetal_WaitForGPU` can wait for everything committed so far.
- One 3D device: the default Metal device, described as `Metal HAL: <GPU name>` (the game picks the device whose
  description contains "HAL"), hardware, with a z-buffer, alpha textures and alpha blending, textures from 1 to
  16384 pixels a side, and no vertex limit, so `std3D_maxVertices` takes retail's default of 512.
- `std3D_Open` makes a scene texture (BGRA8, shared storage) and a depth texture (32-bit float) at the back buffer's
  size, as retail made its Direct3D device and z-buffer on the back buffer surface, and needs the mode to be set
  first, as retail did. It reports the memory figures of P2.8.
- Frame model. Retail's Direct3D drew into the back buffer surface the CPU also locked, so CPU writes and 3D drawing
  landed on one surface. The port keeps two: `std3D_StartScene` uploads the back buffer into the scene texture and
  opens a render pass that keeps that colour, so what the CPU wrote before the scene (the `BackBufferFill` clears)
  lies under the 3D; `std3D_EndScene` submits the pass and makes the scene texture the frame's picture, which the next
  `stdDisplay_Update` presents in place of the back buffer. A frame with no scene presents the back buffer as before.
  CPU writes after the scene (none known yet) and screenshots of a scene (`SaveScreen` reads the CPU back buffer)
  are P2.17.
- `std3D_ClearZBuffer` clears depth to 1.0: inside a scene by ending the pass and opening another that clears depth
  and keeps colour, otherwise at the next `StartScene`. `std3D_Open` leaves a clear pending, as retail cleared Z when
  it created its viewport.
- `StartScene` waits for the GPU before uploading, since the previous scene and its present may still read the scene
  texture. The GPU work per frame is tiny, so this costs nothing measurable; a ring of scene textures can replace it.
- `std3D_BuildDisplayEnvironment` and `std3D_FreeDisplayEnvironment` are the retail bodies (allocated, not the null
  backend's static storage), with allocation checks retail lacked. The texture formats are the null backend's 32 bpp
  BGRA ones, which the material loader already converts to; `GetNumTextureFormats` reports those two.
- Everything else keeps the null backend's behaviour until its step: drawing (P2.11), textures and the cache (P2.12),
  render states and the mipmap filter (P2.13), fog (P2.14), the projection (P2.15), wireframe (P2.16).
- Checked: all tests in the apple, null and sanitizer trees. `boot-sdl` now runs the Metal `std3D` (headless, the
  scenes render offscreen); its autosave is still byte-identical to `boot`'s, and its log adds the display lines and
  `Max vertices: 512`. The `present` test gained a scene step: a scene begins from a pattern in the back buffer, clears
  depth and ends, the back buffer is then painted grey on the CPU, and the presented frame must show the pattern; it
  fails when the scene picture is not handed to the presenter (tried). A windowed game run of 600 frames exits 0.

### Shaders (P2.10)

- `render_metal.m` compiles its shaders from source when the renderer opens and builds two pipelines (flat and
  textured; the textured one is used from P2.12) and two depth states (writes on, and off for P2.13). They stand in for
  Direct3D 6's fixed-function pipeline as retail's `std3D_InitRenderState` set it up:
  - colour = texture × diffuse, alpha the same (`D3DTOP_MODULATE`); the diffuse colour alone when untextured.
    Specular stays off, as retail set `SPECULARENABLE` false; its alpha carries the fog factor (P2.14)
  - alpha test: a fragment passes when its alpha, as 8 bits, is greater than the reference (`D3DCMP_GREATER`,
    reference 0; `0xA0` under `STD3D_RS_ALPHAREF_SET` from P2.13)
  - blending source alpha over inverse source alpha, always on
  - depth test less-or-equal (`D3DCMP_LESSEQUAL`) with writes; no culling (`D3DCULL_NONE`)
- The vertex stage takes rdroid's pre-transformed vertices (`D3DTLVERTEX`) and returns them to clip space: x and y from
  back-buffer pixels to normalised coordinates, shifted half a pixel (Direct3D 6 put pixel centres on whole
  coordinates, Metal at +0.5), then every component times w = 1/rhw, so the divide by w restores the screen position
  and depth while colours and texture coordinates interpolate perspective-correctly (retail turned
  `TEXTUREPERSPECTIVE` on). A vertex with rhw <= 0 is drawn with w = 1. Colours are unpacked from 0xAARRGGBB.
- Depth outside 0 to 1 is clamped, not clipped (`MTLDepthClipModeClamp`): Direct3D 6 did not clip pre-transformed
  vertices on depth. Points are one pixel.
- `J3DRender_Draw` draws indexed triangles, line strips or points into the open scene (wired to `std3D` in P2.11). `std3D_metal.c` checks at compile time that
  `J3DRenderVertex` has `D3DTLVERTEX`'s layout, so rdroid's vertices can go to the GPU as they are.
- A scene keeps the previous depth unless `std3D_ClearZBuffer` asked for a clear, as retail's did.
- `tests/render.c` (apple, no game data, no window) draws into the scene texture and reads it back
  (`J3DRender_ReadScene`). It checks pixel coverage at quad edges, the colour byte order, the depth test in both draw
  orders and at equal depth, a depth clear inside a scene, the alpha test and blending, perspective-correct
  interpolation against the exact formula, depth clamping, and lines and points. It fails without the half-pixel
  shift (5 checks) and without the multiply by w (3 checks); both tried.

### Geometry (P2.11)

- `std3D_DrawRenderList`, `std3D_DrawLineStrip` and `std3D_DrawPointList` keep the retail checks (more vertices
  than `std3D_maxVertices` is an error and draws nothing) and order (`DrawRenderList` sets the render state first), and
  hand rdroid's `D3DTLVERTEX` arrays to `J3DRender_Draw` unchanged. The texture argument is ignored until P2.12, so
  everything draws with its vertex colours (rdroid's lighting).
- Vertex and index data go into one shared buffer per scene, appended draw by draw, 16-byte aligned. rdCache flushes
  a batch whenever it nears 512 indices, so a frame is a few hundred small draws; one allocation per draw would not
  do. `BeginScene` already waits for the GPU, so the arena starts over at every scene. A scene that outgrows it
  (4 MB; a level frame uses far less) continues in a buffer twice the size, and the command buffer keeps the old one
  alive until it completes. The plan called for a ring of per-frame buffers; with the wait at `BeginScene` a single
  arena is enough.
- Screenshots capture what the GPU drew (see "Frame order", P2.17), headless runs included: they render offscreen.
- Checked: frame 300 of `00_cyn` (`jones3d --headless --frames 300 --screenshot-at 300`) shows the canyon's
  geometry, Gouraud-lit, untextured, with walls in front of each other correctly. The `render` test gained a scene of
  50,000 draws (past the arena's 4 MB) whose last draw must land, and a scene after it. `boot-sdl`, which now draws
  every frame, still writes the same autosave as `boot`.

### Textures (P2.12)

- Retail kept two copies of a texture: `std3D_AllocSystemTexture` made a system-memory DirectDraw texture with the
  mip chain (`pD3DSrcTexture`), and `std3D_AddToTextureCache` loaded it into a video-memory one (`pD3DCachedTex`) on
  first use, purging least recently used textures when video memory ran short. On Apple's unified memory one Metal
  texture serves both: `AllocSystemTexture` makes it and uploads the levels, and the cache takes another reference
  (`J3DRender_RetainTexture`). The handle is stored in the `LPDIRECT3DTEXTURE2` fields. The cache list, the
  available-memory count, `PurgeTextureCache`, `ResetTextureCache` and `UpdateFrameCount` are the retail bodies, so the
  game sees the same bookkeeping; with the Metal working set as the budget a purge does not happen in practice.
- RGB textures (`STDCOLOR_FORMAT_RGB`, X8R8G8B8) read as opaque through a texture swizzle whatever their fourth byte
  holds; RGBA textures use their alpha. Retail set a colour key on keyed formats; the port's formats have none (the
  material loader turns transparency into alpha).
- `AllocSystemTexture` keeps retail's skipping of top levels larger than the device allows (none, up to 16384) and its
  single level when the mipmap filter is off. A level not in the renderer's 32 bpp format, or smaller than its mip size,
  ends the chain; a top level of the wrong format is an error and leaves the texture empty, which draws as untextured.
  Retail's rescale of an oversized top level by blit is not needed.
- `std3D_GetMipMapCount` reports the count kept in the texture's surface description, which, as retail's, is 0 when
  the mipmap filter is off.
- `std3D_SetMipmapFilter` (from P2.13's list): none, "bilinear" (the nearest mip level, retail's `D3DTFP_POINT`) or
  "trilinear" (blended levels). Retail fell back when the device lacked a mode; Metal has all three. `std3D_Open`
  sets the bilinear filter and retail's initial render state, as `std3D_InitRenderState` did.
- Samplers: the filter, the wrap or clamp per axis and the mip filter form one Metal sampler, made on first use
  (`J3DRender_SetSampler`); `std3D_SetRenderState` drives the first two from P2.13.
- `std3D_GetValidDimensions` is the retail body against the Metal device's limits; `std3D_FindClosestFormat`
  returns 0 for formats without alpha and 1 with.
- Checked: a headless screenshot of `00_cyn` at frame 300 shows the canyon textured: rock walls, sky, waterfall, and
  the rope ladder's gaps cut out by the alpha test. Frames 10 to 30 are black and frame 45 shows the title logo: the
  opening cutscene's fade, not a fault. The `render` test gained texel placement, wrap, modulation, RGB opacity,
  discarded alpha-0 texels and mip selection.

### Render state, fog, projection and wireframe (P2.13 to P2.16)

- `std3D_SetRenderState` keeps retail's mapping of the changed state bits: `STD3D_RS_ZWRITE_DISABLED` turns depth
  writes off, `STD3D_RS_TEX_CPAMP_U`/`_V` clamp the texture per axis, `STD3D_RS_TEXFILTER_BILINEAR` chooses bilinear
  over nearest texel filtering, `STD3D_RS_ALPHAREF_SET` raises the alpha reference from 0 to `0xA0`, and
  `STD3D_RS_FOG_ENABLED` turns fog on for the draw (with `std3D_bRenderFog`). Retail had one blend mode (source alpha
  over inverse source alpha, always on), so the pipeline cache keyed by blend mode the plan foresaw is not needed: two
  pipelines (flat and textured) cover every state.
- Fog. Retail used Direct3D's table fog: per pixel, linear in eye depth (w) between `FOGTABLESTART` and `FOGTABLEEND`,
  and off entirely when the density is 0 (`D3DFOG_NONE`). The fragment shader does the same, by the perspective-correct
  eye depth. `std3D_SetFog` keeps retail's end depth of `endDepth × (2 − density)`. Retail's per-vertex approximation
  for cards without table fog (`std3D_bFogTable`, which wrote fog into the specular alpha) is not needed.
- Fog density, a retail quirk kept: `std3D_EnableFog` records the density only once a device is open, and
  `JonesDevDialog_LoadSettings` calls it before the display opens, so the saved "Fog Density" does not reach std3D at
  startup; the density stays at its initial 1.0 until the settings dialog changes it. (The renderer's
  `std3D_fogDensity` started at 0 before this step, which would have meant no fog at all; it now starts at 1.0, as
  retail's did.)
- `std3D_SetProjection`: retail gave Direct3D a projection matrix only so table fog could use w for pre-transformed
  vertices; the renderer takes w from each vertex. Retail's checks remain (`DDERR_INVALIDPARAMS`, as `E_INVALIDARG`,
  for a degenerate depth range or field of view).
- `std3D_SetWireframeRenderState` is retail's: fog and the two unknown bits off, no texture.
- Viewport and Retina (P2.15): the viewport is the whole scene texture, the back buffer's size, as retail's was. The
  game window is created with `SDL_WINDOW_HIGH_PIXEL_DENSITY`, so on a Retina display the drawable has the display's
  real pixels and a fullscreen mode at the native size (which the mode list includes) is drawn 1:1; a smaller mode, or
  a windowed one (the window is the mode's size in points), is scaled by the presenter. Mouse positions are converted
  from window points to back-buffer pixels (`J3DApple_WindowToBackBuffer`, `stdDisplay_sdl.h`), so the game's mouse
  messages carry the coordinates it expects in a scaled fullscreen mode too. The development machine's display is not
  Retina, so the 1:1 drawing is by construction, not seen.
- A fault found by the level screenshots, and fixed: the vertex shader drew a vertex with rhw <= 0 at w = 1, which threw
  away the information the GPU needs to clip it. sithRender does not clip world faces against the near plane
  (`rdClip_FaceToPlane` only rejects faces wholly outside the frustum), so floors reaching behind the camera arrive
  with negative rhw and mirrored screen positions; Direct3D 6 clipped pre-transformed vertices in homogeneous space from
  the screen position and w = 1/rhw, which for rdroid's projection is the true camera-space point. With w = 1/rhw kept
  negative, Metal's clip planes cut the part behind the eye off the same way. Before the fix the ground near the camera
  was missing in `16_JEP`, `08_TEO` and `17_PRU`.
- Checked: the `render` test gained a ground plane reaching behind the eye, projected as rdroid projects it (fails
  under the old rule; passes now), depth writes off, the `0xA0` alpha reference, and fog halfway between its depths. The
  `present` test checks the mouse mapping with the window at twice the back buffer's size. Headless screenshots of all
  17 levels at frames 1 and 300 show each level textured and lit, `11_PYR`'s haze, and the near floors restored; the
  all-black frames (`15_AET` at frame 300, `00_CYN` at 10 to 30) are cutscene fades, checked over longer runs.

### Frame order (P2.17)

- How retail built a frame. The game loop (`JonesMain_Process`, open game) does: `std3D_ClearZBuffer`, then, only
  with the `bClearBackBuffer` setting (off by default), `stdDisplay_BackBufferFill(0)`; `std3D_StartScene`; the world
  (`sithDrawScene`), the overlay map, the quicksave text, the HUD (`JonesHud_Process`) and the console (frame rate
  line) are all drawn through `std3D` (rdCache, rdFont, rdWallpaper); `std3D_EndScene`; `stdDisplay_Update`. The load
  screen (`JonesDisplay_UpdateLoadProgress`) and the end credits follow the same shape. Nothing in a game frame is
  drawn on the CPU: the HUD's `rdCanvas` on the back buffer only sets a 3D viewport.
- CPU access to the back buffer happens outside that path: before a scene (the optional clear), in the intro movie's
  blits (`LockBackBuffer`, no scene; Phase 5), and as reads after a scene: the save-game and menu thumbnails
  (`sithGamesave_SetThumbnailImage(&stdDisplay_backBuffer)`, three call sites), `stdDisplay_SaveScreen`
  (the screenshot key, `--screenshot-at`), and in Phase 6 the dialogs' frozen frame (`GetBackBufferDC`).
- Retail's Direct3D drew into the back buffer surface itself, so all of these saw one picture. The port keeps that
  rule with two buffers. `StartScene` uploads the back buffer into the scene texture, so CPU writes before a scene lie
  under it. A frame that drew a scene is presented from the scene texture. Before the CPU touches the back buffer
  again (any lock, fill or blit of it: `J3DDisplay_SyncBackBuffer`), a scene drawn since the last `StartScene` is
  copied into the back buffer, and the back buffer becomes the frame's picture again (`J3DRender_TakeScene`); so a
  CPU read after a scene sees it (thumbnails, screenshots) and a CPU write after a scene lands on it and is
  presented. A fill of the whole back buffer skips the copy, since it overwrites every pixel.
- The copy waits for the GPU and reads the scene texture back (1.2 MB at 640×480). It happens only when the CPU
  touches the back buffer after a scene, which a game frame never does; a save or a screenshot costs one.
- `J3DDisplay_PrepareScreenshot` (P2.11) became `J3DDisplay_SyncBackBuffer`, called from `stdDisplay_VBufferLock`
  (on the back buffer), `stdDisplay_LockBackBuffer`, `stdDisplay_VBufferFill` (so `BackBufferFill` and `ClearRect`)
  and `stdDisplay_VBufferCopy` (either side the back buffer).
- Checked: the `present` test's scene step now fills one quadrant grey after the scene and expects the presented
  frame to show the scene with the grey quadrant on it (it fails without the sync on fills). Headless screenshots
  still show the rendered frame; `boot-sdl` and `boot` saves still match (the level-start autosave is taken before
  the first scene).

### Window behaviour (P2.19)

- Pause on focus loss, as retail: `wkernel_sdl.c` turns a change of focus into `WM_ACTIVATEAPP` and `WM_ACTIVATE`
  (P2.2), and the game's `JonesMain_OnAppActivate` swaps its frame function for `JonesMain_ProcessWindowEvents`, which
  blocks in `wkernel_ProcessEvents` until a window message arrives; game time stops. On reactivation it calls
  `stdDisplay_Refresh(1)` and `std3D_ResetTextureCache`, then resumes. sithTime caps the first frame after the pause at
  200 ms, as in retail.
- Minimizing: a fullscreen game minimizes when another app takes focus (`SDL_HINT_VIDEO_MINIMIZE_ON_FOCUS_LOSS`), as
  DirectDraw's exclusive mode made it. `stdDisplay_Refresh(1)` (retail: restore the cooperative level, the display mode
  and lost surfaces) restores a minimized fullscreen window and makes it fullscreen again. A window minimizes only when
  the player minimizes it; minimizing takes focus, so the game pauses.
- Resizing: a windowed mode's window is resizable. The back buffer keeps the mode's size and the presenter scales it to
  the window; mouse positions follow (P2.15). The window is not resizable in a fullscreen mode.
- Fullscreen toggle: Alt+Return (the Windows convention) or Cmd+Ctrl+F (the Mac's) flips the "InWindow" setting,
  saves it and asks for the game's own display restart (`JonesMain_RefreshDisplayDevice`, handled at the end of the
  frame), as retail's display settings dialog did; the mode the settings name is kept. The key combination is not
  passed to the game. Textures survive the restart: they are Metal textures, not surfaces of the display that closes.
- `stdDisplay_Refresh` left the generated null file (the headless display's does nothing).
- Checked, with temporary local changes (not committed): the toggle triggered at frame 120 of a windowed run turns the
  640×480 window into a 2560×1440 fullscreen one, saves `InWindow=i:0` and exits 0; a focus loss posted at frame 200
  with focus returned a second later (an SDL timer) blocks the next pass for that second with game time unchanged,
  windowed and fullscreen. The keys themselves and real minimizing are checked by hand (scripted input is Phase 3).

### Phase 2 code audit

A final pass over the phase, done 2026-11-13, in five parts.

1. **Warnings the build does not enable.** Everything was rebuilt with `-Wall -Wextra -Wuninitialized
   -Wsometimes-uninitialized -Wconditional-uninitialized -Wcast-align -Wcast-function-type-mismatch -Wshadow
   -Wfloat-conversion -Wimplicit-fallthrough`. The files written in phase 2 (`platform/apple/*`,
   `platform/common/stdDisplay_*`, `host_screenshot.c`, the tests) produce none. In the imported files phase 2 touched:
   `rdModel3.c`'s uninitialised-use reports are in `rdModel3_CalcVertexNormals` and `rdModel3_Write`, which nothing
   calls, and in `rdModel3_LoadEntry`, where `bRGB` is set on every path that reaches its use; the function-type cast
   in `JonesConsole.c` and the fall-throughs in `JonesDevDialog.c` are the retail console and dialog code phase 1's
   audit already classed as safe. The four `-Wcast-align` reports are the blit's typed row access
   (`stdDisplay_VBufferCopy`), aligned by construction: rows are `width × bytes-per-pixel` long from `malloc`.
2. **Static analysis** (`clang --analyze`) of the new platform and renderer files: one report, a null dereference in
   `std3D_RemoveTextureFromCacheList` (the retail body) for a texture not in the cache list. The cache keeps the
   invariant that a texture has a cached handle exactly when it is in the list, and every caller tests the handle

## Phase 3: input

### Key tables (P3.1)

`platform/common/host_keys.c` maps USB HID keyboard usages (which are SDL's scancodes, so the table needs no SDL) to
DirectInput key codes, by position on a US layout as DirectInput's keyboard device reported them, and gives each code
the name Windows' `GetKeyNameText` gave it on a US English keyboard. The Mac's Option keys are `DIK_LMENU`/`DIK_RMENU`
and the Command keys `DIK_LWIN`/`DIK_RWIN` (P3.9); the ISO key left of Return is `DIK_BACKSLASH`, as on a PC. It also
backs two Win32 calls in `crt_posix.c`: `GetKeyNameTextA`, which decodes the scan code and extended bit of a key
message's lParam (the controls dialog names letter keys with it), and `SearchPathA` (P3.7).

### stdControl over SDL (P3.2, P3.4 to P3.6, P3.9)

`platform/apple/stdControl_sdl.c` replaces retail `stdControl.c` and `stdControl_debug.c` (P2.18, removed). It is the
retail file with the DirectInput calls replaced, and keeps its arithmetic: key ids, the pressed-this-frame count, the
share of the frame a key was held, axis registration with centre, scale and dead zone, the mouse's averaging of fast
frames and the axis-as-key thresholds. Each `stdControl_ReadControls` reads one fixed-size snapshot of the devices,
which is also what a recording stores (P3.10):

- **Keyboard**: SDL's keyboard state through the DIK table. Retail read the state too (`GetDeviceState`), so a tap
  shorter than a frame was missed then as now.
- **Mouse** (P3.4): SDL's relative mode while the controls are active, the mouse is read and the window has focus,
  which is what DirectInput's exclusive foreground mouse did (no cursor, motion only). Motion is in points, scaled by
  the new `Mouse Scale` setting (percent, default 100), with the fraction carried to the next read. Buttons and the
  wheel arrive as events from the event loop and are applied in order, as retail applied DirectInput's buffered data,
  so a click shorter than a frame still counts. A click that only focuses the window is not the game's.
- **Controllers** (P3.6): SDL gamepads are laid out as DirectInput showed an Xbox-style pad (left stick X/Y, triggers
  on Z with the left trigger positive, right stick Rx/Ry, buttons A B X Y LB RB Back Start LS RS Guide then the
  extras, d-pad as hat 1). The right stick's X is copied to Rz, the "twist" axis, because the key sets can bind only X,
  Y, Z and Rz. Other joysticks report their first six axes, 32 buttons and four hats as they are. Axes register as
  -32768..32767 with retail's 0.2 dead zone.
- **Hot-plug**: controllers take the lowest free of the 8 slots and keep it while away; a slot that empties releases
  its buttons and centres its axes. `stdControl_GetNumJoysticks` is the number of slots ever used, since the game binds
  per slot. A controller in a slot the game had not seen is announced by the new `stdControl_DevicesChanged`, and
  `JonesMain_ProcessGame` then binds the active key set again (`jonesConfig_RebindControls`).
- **`stdControl_IsGamePad` returns 0.** Retail meant a digital DirectInput gamepad; for one it bound "forward" only as
  walk. An analog controller is treated like retail's joysticks, so its forward axis also binds run at full
  deflection (`jonesConfig_BindJoystickControl`): walking at part deflection, running at full.
- **Activation** (P3.9): the window's focus is passed in from the event loop; Cmd-Tab and any other loss of focus
  release the mouse at once, besides the game's own `stdControl_SetActivation(0)`. Cmd-Q is SDL's quit (P2.2).

Retail faults kept out of the port, each marked `// Port:`:

| Where | What retail did | Now |
| --- | --- | --- |
| `stdControl_ReadControls` | `1.0f / readDeltaTime` with no guard: infinity for two reads in one millisecond | 1 for a zero delta. On the virtual clock (headless, replay) two reads in one frame are common. |
| `stdControl_ReadAxisAsKey` | Indexed `stdControl_aAxes` with the axis id still carrying its flag bits, far past the array | The flags are masked off first. |

Kept as retail: `memset` of 7 *bytes* of axis state when mouse sensitivity is on, and `ReadAxisAsKeyEx` never setting
`*pbPressed`.

### Window messages (P3.3)

`WM_KEYDOWN`/`WM_KEYUP` now carry the scan code (bits 16-23) and extended flag (bit 24) from the DIK table. Typed text
already arrived as `WM_CHAR` (P2.2); the console reads it.

### Key sets (P3.7, P3.8)

The retail `.kfg` files are copied into `<Install Path>/KeySets/` on the first run (P1.19) and loaded through
`SearchPathA`, which was a null stub until now, so no key set file had ever been read by the port. Reading one
exposed two retail faults, both fixed in `jonesConfig_LoadControlScheme`:

| What retail did | Now |
| --- | --- |
| Passed `(size_t*)&argNum` for an `int argNum` to the argument parsers, which wrote 8 bytes into it: on arm64 the parse ran off the end of the argument list and crashed | `argNum` and `prevArgNum` are `size_t`. |
| Copied the whole file path less `.kfg` into the scheme's 128-byte `aName`: it fit under a short Windows install folder, but a macOS user folder overruns the heap block | The file name alone, bounded. The controls dialog loads key sets by bare file name, so that is what it had there. |

Three of the eleven retail key sets ("Gravis GamePad Pro", "MS SideWinder Precision Pro", "MS SideWinder game pad")
lack the "1" (enabled) line that the parser requires, so the retail game rejected them too; the other eight load.

P3.8, the port's default for a modern controller ("Dual-Stick Controller", `jonesConfig_aPortDualStick`): chosen when no
key set is configured and slot 0 holds a two-stick controller, and by name afterwards. It is kept apart from the three
retail defaults so the controls dialog's handling of those (Phase 6) is unchanged. The bindings are listed in
BUILDING.md, "Controls". `Joystick Control` now defaults to on (`JonesControl_Startup`): retail's player turned it on
in the controls dialog, which arrives in phase 6.

### Recording and replay (P3.10)

`platform/common/host_record.c`, `--record`, `--replay`, `--input-script` (BUILDING.md). A run is repeatable when
everything it reads from outside is; the engine's random generator already is (P1.24), so a recording holds the clock
at each present, each pass of the event pump, each window message that came from outside the game (keys, characters,
mouse, activation, timers, close) and stdControl's snapshot at each read, in the order the game asked for them. A
replay supplies the same values and checks the kind of each record; a mismatch stops it at that frame with a
failure exit.

The clock needs care. A played recording runs on the new frame clock (`host_clock.h`): virtual time that stands still
within a frame, moves to the host's time at each present and also moves (and waits) in `Sleep`. Every value the game
reads is then one the recording holds, and a replay sets them on the plain virtual clock. A headless recording keeps
the headless fixed step. The display backends call `J3DRecord_Present` instead of moving the clock themselves.

Limits: a recording belongs to the build, data and settings it was made with; window resizing and painting are not
recorded (they do not change the game); the controls dialog's own input (Phase 6) will need its messages to go
through the same pump.

## Phase 4: audio

### miniaudio (P4.1)

`third_party/miniaudio/`: miniaudio 0.11.25, unmodified, with its licence (public domain or MIT-0) and the source and
SHA-256 of each file in `README.port.md`. It is compiled once (`miniaudio.c`) as its own target, without the
project's warning flags, with only the playback device and the Core Audio backend; the switches are the target's
public compile definitions, so every file that includes the header sees the same structures. Only the apple build
links it: `platform/apple/audio_device_ma.c` is the output device. The null build has no device
(`platform/common/null/audio_device_null.c`). Between them and the mixer is `platform/common/host_audio.h`.

### Opaque handles (P4.2)

`sound/types.h` declares `SoundDevice` and `SoundVoice`; `LPDIRECTSOUND` and `LPDIRECTSOUNDBUFFER` are gone from
`Driver.h`, `Sound.h` and `Sound.c` (a rename, no behaviour), and so is `<dsound.h>`.

### The sound driver (P4.3 to P4.6)

`platform/common/SoundDriver_mix.c` implements `Libs/sound/Driver.h` (retail `Driver.c` stays excluded; the generated
`SoundDriver_null.c` is gone). It is in `platform_core`, so the null build, the tests and the headless runs use the
same driver as the game.

**Which DirectSound it is.** Retail's driver had two paths. With 3D sound hardware and the "3D sound" option, mono
buffers were DirectSound 3D buffers placed by the hardware; otherwise, and for every stereo buffer, the driver asked the
game for a channel's volume and pan (`sithSoundMixer_CalcCameraRelativeSoundMix`) and set them on plain buffers. The
port's driver is the second path: `SoundDriver_Has3DHW` and `SoundDriver_Use3DCaps` are 0, so the options dialog greys
its 3D check box as on a retail machine without 3D hardware, and every sound is placed by the game's own mix. Reasons:
that mix is complete and is what the game's designers tuned; there is no 3D sound hardware on a Mac to emulate; and
the 3D path's listener is set up oddly in retail (`Sound_Update` negates both the front and the top vector, which
leaves DirectSound's right vector, top × front, unchanged; with the game's axes that vector is -x, the camera's left).
Not emulating it is decision 19 in PORT-PLAN.md. The listener, 3D buffer and global functions keep their values
and do nothing else; `Update3DSound` is retail's software half.

**Two clocks.** What the sound module can observe of a voice (playing or not, its play cursor for lip sync) is
computed from `SoundDriver_GetTimeMsec`, the engine clock: the position moves by frequency × elapsed time while the
voice plays, a one-shot stops at its end with its cursor back at 0, a loop wraps, `Stop` holds the position and `Play`
resumes it, a frequency change applies from when it is made. The device renders from a cursor of its own, in real
time, and is never asked. So a headless, recorded or replayed run sees exactly the same sound state every time (saves
and recordings stay byte-identical, `boot` and `boot-sdl` write the same autosave as the null build), and the null
build, with no device, runs the sound module unchanged. The two cursors can differ by a few milliseconds; a voice the
game releases stops rendering then.

**The mix.** Each voice's PCM is copied at creation (DirectSound copied it into the buffer too), converted to 16-bit
(8-bit samples centred on 128), and decompressed first when it is one of the sound module's compressed sounds.
Volume and pan are DirectSound's: hundredths of a decibel, the minimum silent, pan attenuating the far side. The
renderer interpolates linearly between source frames at frequency / 48,000 and sums into float stereo; miniaudio
clamps to ±1, as DirectSound's software mixer saturated. A lock guards the voice list against the device thread;
the game thread holds it only for a few stores at a time. While the window is in the background a voice not made
with global focus is silent but keeps moving, as DirectSound did (`J3DAudio_SetFocus` from `wkernel_sdl.c`). The
game itself stops its loop on deactivation (`JonesMain_OnAppActivate`) but does not pause the sound module, so this
mute is what silences sounds that are still playing. DirectSound's argument checks are kept where the game can reach them: a
frequency outside 100 Hz to 100 kHz is refused (0 restores the buffer's own), formats other than 8- or 16-bit mono or
stereo are refused. `DuplicateSoundBuffer` is emulated (shared PCM) though `Sound_Play` never asks for it.

Retail code kept unchanged in the new file: the decibel table, `InitPanTable` and the four conversion functions
(P4.5), `CalcListeneSoundMix`, `CalcDistToListener` and `Update3DSound`. Two changes, marked `// Port:`:

| Where | What retail did | Now |
| --- | --- | --- |
| `SoundDriver_Update3DSound` | Left `newVolume`, `pan` and `newPitch` unset before calling the game's mix, which returns without writing them when there is no camera; the far-sound check then read stack garbage | They start as the unplaced values (the given volume, centre, 1). |
| `SoundDriver_CalcListeneSoundMix` | Left `SoundSpatialInfo`'s three unknown fields unset | Zeroed. |

Kept as retail and noted for the phase 8 fix series: `SoundDriver_GetIntPan(1.0)` indexes past the pan table and
returns 0, so a sound exactly to the camera's right is centred; `SoundDriver_GetPan` returns 0 (retail's linker

### Startup (P4.7)

`SoundDriver_Open` succeeds with or without a device, so `Sound_Open` succeeds: no `JONES_STR_SOUNDERROR`, and

### AudioLib (P4.8)

`AudioLib_UncompressBlock`'s ADPCM decoder was hand-written x86 in retail, translated to C in phase 0. There is no
Windows build to take reference output from, so the check uses the encoder as the oracle: retail's
`AudioLib_CompressBlock` tracks the decoder's reconstruction sample by sample. `tests/sounddriver.c` compresses
twelve signals (silence, quiet and full-scale tones, noise, full-scale steps that force escapes; mono and stereo),
decodes them with the translated block, and compares with an independent decoder written from the encoder's
arithmetic: bit for bit equal, and the decoder ends in the state the encoder ended in. Reading the assembly again
against the C found no difference (the delta table is `uint16_t`, matching the `movzx` that reads it). This decoder
serves only the >2-channel block format; the game itself compresses through WVSM (`AudioLib_Compress` with 1 or 2
channels), which retail wrote in C, and which a boot exercises.

| Where | What retail did | Now |
| --- | --- | --- |
| `AudioLib_WVSMCompressBlock` | `*pCurOut++ = *pCurOut++ = 0;`, two unsequenced increments (undefined; the one `-Wno-error` left from phase 1) | Two stores. Only the count matters: the decoder reads and discards both bytes. `-Wno-error=unsequenced` is removed from `CMakeLists.txt`. |

| `AudioLib_GenerateLipSynchBlock` | Read 16-bit samples through `int16_t*` from an odd address (`Sound.c` always passes `bSkipFirstByte`), and with the skipped byte uncounted, read one byte past the sound data (ASan) | Byte pointers and `AudioLib_Load16`; the size drops by the skipped byte and the whole-file pass stops one sample earlier.
